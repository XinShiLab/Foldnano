# Sequence CSV Export

Sequence CSV export writes one row per oligo with explicit 5' and 3' endpoint
labels:

```text
Start,End,Sequence,Length,Color,Mod5Prime,Mod3Prime
```

The exporter is intentionally an endpoint-oriented format. Every exported oligo
must have a concrete free 5' end and free 3' end. Circular DNA is rejected before
download, for both scaffold and staple oligos. The scaffold is included in the
CSV when export succeeds, so its endpoints must be explicit too.

The `/oligos/[docId]` report page is display-only and can show circular oligos
for inspection with `Circular` endpoint labels and segment positions. Its
`Download CSV` action still uses this strict exporter, so circular oligos are
rejected there the same way they are rejected from the editor toolbar.

The report page currently reads `document.parts[0]`, matching the editor's
current one-part working assumption.

`collectPartOligoSequences` iterates `part.realOligos` (mirror oligos — repeat-unit copies, see
`docs/repeat-units.md` — excluded), not `part.oligos`, so repeat mirrors never appear as CSV rows.

## Circular DNA Policy

Foldnano does not infer a cut point for oligo CSV export. Circular oligos have no
canonical 5' or 3' terminus, and choosing a representative segment would make the
CSV sequence depend on an implicit, format-specific convention. Users must first
break circular DNA into a linear oligo when they want sequence CSV output.

This is an architecture decision:

- circular scaffold CSV export is unsupported
- circular staple CSV export is unsupported
- scaffold rows are included in the CSV, so scaffold endpoints are not optional
- UI export actions must show an error and avoid producing a file when any
  circular oligo is present
- model-level CSV collection must also reject circular oligos, so callers outside
  the toolbar cannot accidentally export guessed endpoints

Other exporters can use different topology semantics. For example, simulation
exports can preserve circular backbone connectivity because their formats encode
neighbor links directly. Oligo CSV does not.

## Correctness Checks

The sequence-generation correctness check lives in
`src/lib/model/test/sequence-comparison.spec.ts` (comparison logic under
`src/lib/model/test/sequence/`). It compares Foldnano-generated oligo sequences
against cadnano 2.5 over all ten designs in `test_files/published_cadnano_designs`,
writing `sequence-comparison-report.md` and `.json` under
`test_files/fixtures/sequence_generation/`.

Both sides start from the same original design file and the same test scaffold,
`scaf8634`. The reference CSVs in
`test_files/fixtures/sequence_generation/cadnano_ref` are generated by
`scripts/gen_reference_sequences.py` from cadnano's own `Oligo.sequenceExport`
(not `Oligo.sequence()`, which silently drops sequenced bases past an
unsequenced 5'-most strand). The generator also writes `_provenance.json`,
recording the scaffold, the circular break point, per-design counts, and
content hashes of every input and output, normalised for line endings; the spec
reads and verifies all of it, including a pinned commit and patch-file hashes
for the approved cadnano build, so the two sides cannot drift onto different
inputs unnoticed.

For circular scaffolds, both the Python reference generator and the TypeScript
spec linearize at VH0's incoming crossover before applying scaffold sequence.
That VH0 rule exists only inside the test/reference-generation path for published
cadnano designs, where a consistent artificial break is needed to compare
Foldnano output with cadnano 2.5. It must not be used by the app as an export
policy. In the app, even the same design must ask the user to break the circular
strand and indicate explicit 5'/3' ends before oligo CSV export.

That check proves the linearized scaffold-to-staple sequence propagation path,
not arbitrary circular-oligo CSV export or app-level circular scaffold support.

```bash
# regenerate the reference CSVs (needs a local cadnano 2.5 checkout, see below)
CADNANO_PATH=ref_cadnano25 python3 scripts/gen_reference_sequences.py

# regenerate the report
UPDATE_SEQUENCE_REPORT=1 pnpm vitest run src/lib/model/test/sequence-comparison.spec.ts
```

`scripts/gen_reference_sequences.py` needs a cadnano 2.5 git checkout: it looks
at `$CADNANO_PATH`, then `./ref_cadnano25/` (`ref_*` is gitignored). cadnano 2.5
predates modern numpy/PyQt5 and needs two source patches to import on Python 3.13
(`inner1d` removed from numpy, a float font size rejected by PyQt5); the patched file hashes are pinned in
`APPROVED_CADNANO` in both the generator and the spec, so an unapproved build is
rejected rather than silently used.

Which checkout to use:

- **Approved build (reproduces the committed fixtures):** the original
  [cadnano/cadnano2.5](https://github.com/cadnano/cadnano2.5) at commit
  `ce6ff019b88ee7728de947bd86b35861cf57848d` (v2.5.2.1), plus the two patches
  above:

  ```bash
  git clone https://github.com/cadnano/cadnano2.5 ref_cadnano25
  git -C ref_cadnano25 checkout ce6ff019b88ee7728de947bd86b35861cf57848d
  # then apply the two patches
  ```

- **Maintained alternatives:** [douglaslab/cadnano2.5](https://github.com/douglaslab/cadnano2.5)
  or the lightweight fork [xinshi-kul/cadnano2.5_mini](https://github.com/xinshi-kul/cadnano2.5_mini)
  (the source of the bundled `cadnano2_5_mini` plugin wheel). Neither contains the
  approved commit, so the generator rejects them unless `ALLOW_UNAPPROVED_CADNANO=1`
  is set. Switching to one means regenerating the fixtures and updating the pins in
  `APPROVED_CADNANO` (generator) and `sequence-comparison.spec.ts` together.

## Boundaries / Don'ts

- Don't add fallback endpoint labels for circular oligos.
- Don't export circular staples by picking the first segment in iteration order.
- Don't export circular scaffolds by applying the VH0 test break convention.
- Don't use `Oligo.isScaffold` to decide whether circular DNA is allowed; all
  circular oligos are rejected for sequence CSV.
- Don't treat the cadnano sequence reference suite as coverage for circular CSV
  rows. It validates linearized sequence assignment and staple comparison.
- Don't hand-edit `cadnano_ref/*.csv` or `_provenance.json`; regenerate them.
- Don't let the spec pick its own scaffold or circular break point; both come
  from `_provenance.json`.
